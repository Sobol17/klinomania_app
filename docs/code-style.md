# Code Style

Документ фиксирует правила написания кода в проекте `klinomania`. Цель — простой, предсказуемый и поддерживаемый код без лишних ветвлений, дублирования и скрытой сложности.

## Базовые принципы

### DRY

- Не дублируйте бизнес-логику, форматирование, маппинг и проверки в разных местах.
- Если одинаковый код появился второй раз, проверьте, можно ли вынести его в helper, mapper, formatter, виджет или метод контроллера.
- Не создавайте абстракцию заранее. Выносите общий код только тогда, когда повтор уже есть или повторение очевидно усложняет поддержку.
- Общие элементы фичи держите внутри фичи. В `shared` выносите только то, что реально используется несколькими фичами.

### KISS

- Выбирайте самое простое решение, которое закрывает текущую задачу.
- Не добавляйте слой, класс, enum, callback или состояние без понятной причины.
- Предпочитайте прямой читаемый код сложным универсальным механизмам.
- Не проектируйте код под гипотетические сценарии, которых нет в требованиях.

### SRP

- Один класс, метод или виджет должен иметь одну ответственность.
- UI строит интерфейс, контроллер управляет состоянием, репозиторий скрывает источник данных, mapper преобразует модели.
- Не смешивайте сетевые запросы, форматирование, навигацию и бизнес-правила в одном методе.
- Если метод сложно назвать коротко и точно, скорее всего он делает слишком много.

## Null Safety

- Не добавляйте проверки на `null`, если тип не nullable.
- Не используйте fallback-значения `?? ''`, `?? 0`, `?? []` без продуктовой причины.
- Не скрывайте некорректные данные молчаливыми fallback-ами. Лучше явно нормализовать данные на границе слоя или показать ошибку.
- Nullable-поле используйте только когда отсутствие значения является валидным состоянием.
- После валидации значения делайте код линейным: ранний `return` лучше вложенных `if`.

Пример:

```dart
if (profile == null) {
  return;
}

showProfile(profile);
```

Не нужно:

```dart
showProfile(profile ?? ClientProfile.empty());
```

## Именование

- Используйте простые и короткие имена без лишних слов.
- Имя должно отражать смысл в текущем контексте, а не всю историю объекта.
- Не добавляйте префиксы вроде `current`, `selected`, `active`, если без них значение не теряет смысл.
- Для классов используйте принятые суффиксы проекта: `Controller`, `Repository`, `RepositoryImpl`, `RemoteDataSource`, `Model`, `Page`.
- Для boolean-полей используйте понятные формы: `isLoading`, `hasError`, `canSubmit`.
- Не используйте сокращения, которые не являются общепринятыми в проекте.

Пример:

```dart
final order = orders[index];
final canSubmit = name.isNotEmpty && email.isNotEmpty;
```

Не нужно:

```dart
final currentlySelectedOrderItemModel = orders[index];
final isUserAllowedToSubmitRegistrationForm = name.isNotEmpty && email.isNotEmpty;
```

## Методы и функции

- Метод должен быть коротким и выполнять одну задачу.
- Используйте ранние выходы для ошибок и невалидных состояний.
- Не передавайте лишние параметры. Если метод не использует значение напрямую, параметра быть не должно.
- Не возвращайте `null` как универсальный сигнал ошибки. Используйте понятный результат, исключение или состояние контроллера.
- Не смешивайте вычисление данных и побочные эффекты. Сначала посчитайте значение, затем примените его.

## Виджеты

- Разбивайте большие экраны на приватные виджеты по смысловым блокам.
- Не выносите виджет только ради уменьшения строки, если он используется один раз и не несет отдельной ответственности.
- Не дублируйте одинаковую разметку. Повторяющиеся поля, плитки, карточки и строки выносите в маленькие виджеты.
- Состояние держите как можно ближе к месту использования.
- Не храните в state то, что можно вычислить из текущих props/controller.

## Контроллеры и состояние

- Контроллер должен описывать состояние фичи и действия пользователя.
- Не кладите в контроллер форматирование UI-текста, если оно относится только к одному экрану.
- Не храните дублирующее состояние. Если значение можно вывести из другого поля, сделайте getter.
- Сбрасывайте ошибки и loading-состояния в одном месте, чтобы не расходились сценарии успеха и ошибки.
- Не вызывайте `notifyListeners()` чаще, чем требуется для обновления UI.

## Data и Domain

- Domain не должен зависеть от Flutter UI, API-клиентов и локального хранилища.
- Data-layer отвечает за API, локальное хранение и преобразование внешних данных во внутренние модели.
- Маппинг из JSON держите в `Model`, маппинг в сущность — рядом с моделью или в отдельном mapper, если логика растет.
- Не протаскивайте API-ключи и временные поля в domain, если бизнес-логика их не использует.
- Fallback-и для внешних данных допустимы только на границе data-layer и должны быть осознанными.

## Проверки и ошибки

- Проверяйте только реальные невалидные состояния.
- Не добавляйте защитные `if`, которые невозможны по типам или контракту метода.
- Сообщение об ошибке должно соответствовать действию пользователя.
- Не подавляйте ошибки пустыми `catch`. Минимум — сохранить состояние ошибки, максимум — пробросить выше.
- Не используйте общий fallback там, где можно показать конкретную причину.

## Комментарии

- Комментарий нужен для причины, ограничения или нетривиального решения.
- Не комментируйте очевидный код.
- Если код требует длинного комментария, сначала попробуйте упростить код или имя метода.

## Перед завершением задачи

- Запустите `dart format lib`.
- Запустите `flutter analyze`.
- Для новой логики добавьте тесты или явно зафиксируйте, почему тесты не добавлены.
- Проверьте, что новая логика не дублирует существующие helpers, widgets, mappers и controllers.
